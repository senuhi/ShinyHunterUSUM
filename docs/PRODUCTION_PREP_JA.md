# 本番準備：ベベノム／タイプ：ヌル（ポニの古道）・手持ち1匹

v1.4のアプリ内実行は [APP_HUNT_JA.md](APP_HUNT_JA.md) が入口です。以下の開始位置・手持ち条件は共通です。

## 確定した方針：上流のベベノム／ポニの流れを使う

本番対象は **ベベノム、タイプ：ヌル（ポニの古道）** の2ルートです。
エーテルへの持ち越しは取りやめ、ボックス満杯の準備は不要です。
日本語GUIはこの2対象を表示し、英語版の既存エーテル機能は残します。

受取前は手持ち1匹、受取後の対象は2番目になります。4匹へ揃える必要はありません。
残す1匹は受取対象と別種にし、文字速度は「はやい」、BoostはOFFです。
通常メニューは「ポケモン」、手持ちカーソルは先頭を使います。
手持ち一覧を開いた後は、Mac上で検証した選択処理を使い、右・A・Aで2番目の情報画面を開きます。

## 保存位置と事前状況

| 対象 | 準備して保存する状態 | 上流のイベント開始処理 |
| --- | --- | --- |
| ベベノム | まだ受け取っていないウルトラ調査隊の受取NPCの正面。Aで受取会話を始められる向き・距離。会話なしで保存 | 移動なし。Aで名前が出る会話まで進める |
| ヌル・ポニ | 殿堂入り後のビッケ／ハウの受取イベント前。イベント境界のすぐ左側、右へ少し進むと始まる位置。会話なしで保存 | 右へ0.1秒入力→中立を3回。その後Aで対象名の会話まで進める |

上流READMEも、ベベノムはNPC前、ポニのヌルはイベント境界の左で保存する指定です。
[固定した上流版のREADME](https://github.com/u93132/ShinyHunterUSUM/blob/f49910affd7ed35b38af8e2b5b35499dcc554f0d/Readme.md)
と、同版の `Recv.findrecv` / `nav_dialogue` / `check_summary` が根拠です。
ポニについては以前の「全ルートNPC正面」という条件を置き換え、上流の開始位置に合わせます。

ベベノムはウルトラネクロズマ撃破後、初回の受取を後回しにしてから、改めて話しかける直前を用意します。
[実際の受取・厳選の記録](https://ameblo.jp/14750mk/entry-12331673006.html) でも一度断って保存する手順が説明されています。
ポニは近づくだけでイベントが始まるので、境界へ入る前の未受取状態を保存してください。
[ポニの保存位置と右移動の実例](https://marumero197.com/772-usum/) も参考になります。
最終的な境界との距離は、保存後の実機映像で確認し、上流の短い右入力でイベントが始まる位置に合わせます。

各ルートの未受取セーブは保持してください。同じデータで先のストーリーへ進む場合も、
厳選に戻るための受取前状態を失わないよう、手元の保存・バックアップ方針に合わせて進めてください。

## 再利用する処理と日本語版の調整

- ベベノム：Aで対象名の会話→Bで手持ち追加の表示まで進める。
- ポニのヌル：右移動3回→Aで対象名の会話→Bで会話末尾まで進める。
- 共通：Bで会話を片付ける→Xでメニュー→ポケモン→受取個体の情報画面。
- 判定後：通常色を再確認した場合だけリセットし、元の受取前セーブへ戻る。

旧テンプレート方式の `GiftRunner.receive` には上流の分岐を残しています。
v1.4の日本語専用アプリは、同じポニの右進入・Aで受取・Bで会話を片付ける順序を土台に、
日本語の明確な受取完了文をローカルOCRで確認してから情報画面へ進みます。
名前が出る位置の違いによって受取をキャンセルしないよう、英語座標の単純な流用はしません。
入力・受信・情報画面・赤星・通常色再確認・リセット／復帰は既存の共通処理を再利用します。

`profiles/production-ja.json` に各ルートの開始条件・移動・受取分岐と上流の参照元を記録しました。
本番2対象の実機1周はアプリ上で確認する段階です。操作者の指示により、実物色違いを出すことは開始条件にしません。
旧テンプレートの校正済み記録は発行せず、専用アプリの実行と確認範囲を別に記録します。
上流のルート処理とMac側の移動／会話分岐をモックで直接比較する回帰テストを追加しています。
これは、上流の実績を日本語版・Old 3DSでの動作確認済みとみなすものではありません。

## 主判定は情報画面の星

ベベノムの紫／白やヌルの灰色／黄色を、リセットの唯一の根拠にはしません。
対象名と情報画面の目印を確認し、色違い星の表示範囲と既存8×8パッチを調べます。
赤星候補は通常色のパッチ結果より優先します。赤い点があるが星と決めきれない場合もunknownにします。
星が出る別位置を見落とし、空いた緑色のパッチだけを通常色としてリセットすることを防ぎます。
最後は3つの新しい両画面の一致と、リセット直前の新しい両画面での再確認が必要です。
対象名違い・星の不明瞭さ・不一致・映像停止・通信断ではリセットしません。

設定は `profiles/poipole-summary-ja.json` と `profiles/typenull-poni-summary-ja.json`。
星の探索帯は下画面 [40,176,85,202]、既存パッチは [59,184,67,192] です。
どちらも実機画像に合わせて校正する仮値です。小さい赤い図形は「色違い候補」であり、形だけで精度を保証しません。
初期は送信0の接続確認と情報画面停止を選べます。通常色のリセット／周回は専用アプリの開始操作で選択します。

## 提供された画像の位置付け

最初の4枚は図鑑登録画面です。体色の参考にはなりますが、情報画面の星の教師画像とは別です。
ヌルの頭と尾で簡単な黄色の指標 `(R+G)/2-B` を測ると、この4枚では次の差がありました。
同じ画像から選んだ領域の参考値であり、未知画像の精度や本番しきい値を表しません。

| 部位 | 通常色 | 色違い |
| --- | ---: | ---: |
| 頭の灰／黄の部分 | -4.76 | 32.53 |
| 尾のヒレ | -5.62 | 67.82 |

肉眼では近くても数値差はあります。ただしモデルの向き、明るさ、輪郭、YouTubeの圧縮、
ChirunoModのJPEGによって値が変わります。補助検討では頭・尾の複数箇所と複数フレームを使い、
背景や陰影を混ぜず、曖昧な値を通常色へ丸めません。**体色の参考画像からリセットは許可しません。**

追加の赤星画像は情報画面の正例です。画像819×617を分析用に320×240へ換算すると、
赤い成分は [47,188,53,194] にありました。既存のUSUM用パッチと位置が異なり、
上流が併記するもう一つのUI配置に近いため、画像のゲーム版や座標を無条件には同一視しません。
探索帯の赤星候補として検出でき、以前の実機通常色ピカチュウでは赤星候補なしを確認しました。
これは保存スクショでの検出確認であり、自分の3DSの色違いを受信して検証した結果ではありません。
スクショ原本・個人の実機画像はGitへ追加していません。

## データ準備後に行うこと

1. 各ルートの受取前データで上流のイベント進入・A/B進行と日本語の目印を確認する。
2. 手持ち1→2匹で正しい対象の情報画面へ到達することを確認する。
3. 原寸の上400×240／下320×240を保存し、対象名・星の位置・通常色を送信0で再判定する。
4. 正例・負例・星の位置ずれ・欠けた映像・判定の不一致で安全停止を確認する。
5. 通常色だけのリセット・復帰・完了集計を少数周確認してから連続運転へ進む。

本物の色違いがない間も提供画像を参考正例にできますが、実機の色違いでの検証完了とは記録しません。
正常色が確認できない回はリセットせず止めます。

準備条件の確認と、保存した原寸情報画面のオフライン再判定は以下です。どちらも操作を送りません。

```sh
.venv/bin/python gift_tools.py prepare
.venv/bin/python gift_tools.py summary-replay --target poipole \
  --upper captures/upper.png --lower captures/lower.png --output captures/poipole-summary.json
.venv/bin/python gift_tools.py summary-replay --target typenull_poni \
  --upper captures/upper.png --lower captures/lower.png --output captures/typenull-summary.json
```

再判定の一組は連続フレーム検証やliveの許可ではありません。出力の `reset_authorized` は常にfalseです。
大きさの違うYouTubeスクショをこのコマンドで本番用の原寸画像として扱うことは拒否します。
