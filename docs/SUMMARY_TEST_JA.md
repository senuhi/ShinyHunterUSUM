# ピカチュウで情報画面まで検証する

この診断は日本語USUMの受取後の操作と判定経路を確認するためのものです。
ベベノム／タイプ：ヌルの本番厳選や、実際の色違いでの精度確認とは区別します。
初期設定の「情報画面で停止」は、受取・メニュー操作は許可を受けて実行しますが、
リセットは送りません。接続確認だけの場合はボタンも送りません。

## 同じ開始状態を使う

開始は受取前に手動保存した受取員の前・会話なしに統一します。
通常メニューは「ポケモン」、手持ちカーソルは先頭にしておきます。
受取前の手持ち数を1〜5で指定します。操作者の現在のデータは4匹です。
受取個体を最後の空き枠へ追加し、先頭から2列×3行の配置を固定キーで移動します。
4匹なら受取個体は5番目なので、下・下・A・Aで「つよさをみる」を開きます。
この実機操作の到達はこれから確認します。途中のメニューを画像で押し進める処理はありません。
位置や選択が違っていても、情報画面の判定が不明ならリセットは許可されません。

## 判定と証跡

`profiles/pikachu-diagnostic-ja.json` に座標と色の設定があります。
`colour.screen` は0=下、1=上、`colour.box` はネイティブ解像度の [左,上,右,下] です。
出荷値の下画面 [59,184,67,192] とnormal/shinyのRGBは上流Recv.pyのUSUM用参照を流用しています。
日本語版の座標やChirunoModの色分布を実機確認した値ではありません。
色違い画像を持っていないため、実際の色違い検出は検証できていません。

対象名「ピカチュウ」のOCRスコア0.9以上に加え、おや・ID・経験値・次のレベルの
4群から2群以上（スコア0.8以上）を要求します。名前だけの手持ち一覧は情報画面と認めません。
色比較は本番側と同じ `gift_recognition.colour_verdict` を使用します。
通常色・色違い双方への距離、距離差、画素のばらつきで判定し、どちらにも近くない場合はunknownです。
3つの新しい両画面で判定が一致しなければ停止します。スコアは確率ではありません。

記録フォルダに次を保存します。

- `summary-1/2/3-0/1.png`: 各判定の両画面。
- `events.jsonl` の `summary_verdict`: OCR結果、目印、RGB平均、通常色／色違い距離、ばらつき、設定ハッシュ。
- `report.json`: 最新の判定・送信数・リセット数・完了周回数。
- `summary-final-reset-check-0/1.png`: リセットを許可した場合の最終判定画像。

初回は情報画面停止のまま、5番目の受取個体が表示されているか、色領域が星の位置に
合うか、通常色の結果が正しいかを確認します。ずれていれば記録画像に基づきJSONを変更し、
同じ保存位置へ手動で戻して再試験します。色参照は多数の画素から勝手に学習しません。
実際の色違い・負例・3ルートの素材が揃うまでは、本番の校正完了にはしません。

## 1周の試験

情報画面の到達・領域・判定を確認した後に限り、受取前の同じ保存位置へ手動で戻り、
接続確認からやり直します。「情報画面で停止」をOFFにして今回の実行を許可すると、
通常色3フレーム一致→新しい両画面で通常色の最終再確認→リセット1回となります。
色違い候補、unknown、判定不一致、解析中の鮮度切れ、通信異常ではリセットしません。
リセット後は固定待機とSTART・Aだけで復帰し、上画面の保存場所を新しい3フレームで確認します。
下画面のロトムの自発的な質問は場所の復帰判定には使いません。
ゲーム内セーブやリセットの再試行はありません。
